# R0｜一页结论

## 核心结论

我建议将 Herdr Mobile 从“远程 Agent 看板”，重新定位为“移动端 Agent 控制中心（Agent Command Center）”。

产品的首要对象不应该是 Agent，也不是会话，而是：

一个等待人类作出决定、才能继续推进的工作事项。

这会改变首页、导航、通知、审批、数据模型，甚至主机端架构。

产品：Attention-first

首屏直接显示需要处理的事项，其他 Agent 收进次级视图。借鉴 Linear Inbox、Slack Activity，而不是复制 SSH 客户端首页。

客户端：保留 Kotlin + Compose

不因为旧 UI 卡顿就更换框架。重建交互、状态管理和渲染边界，先实现 Android 品质，再预留 iOS 共享核心的可能性。

连接：主机侧轻量 Companion + 直连优先

由主机组件负责事件聚合、对话增量、结构化审批和消息回执。SSH 继续作为安全传输及兼容回退；以后可选加密中继和推送。

## 三条最关键的理由

1\. 当前最重要的问题，是产品的主对象选错了。[推断]

现有首页按照 `blocked / working / done / idle / unknown` 分组，相当于让用户主动从运行状态里寻找待办事项。

而 Linear 的 Inbox 和 Slack 的 Activity，都把“需要采取行动的事情”单独聚合起来。Cursor 的移动端也已将 Agent 状态、输入和工作成果审阅组合到移动工作流中。

[image](https://www.google.com/s2/favicons?domain=https://linear.app\&sz=32)

Linear Docs+2



2\. 仅重做 UI，无法解决交互延迟与后台通知。[事实 + 推断]

你提供的实测显示，单个 API 请求需要约 300–500 ms，SFTP 轮询对话一次有 5–8 个网络往返。加上结构化审批依赖额外 hook 文件轮询，现有系统很难做到稳定的即时交互。

而 benkraus 的 Herdr Mobile Relay 已公开演示了主机侧 REST/WebSocket 桥接、实时终端增量和鉴权的做法。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

benkraus/herdr-plugin-mobile-relay · GitHub+1



3\. 没有证据表明 Compose 本身就是卡顿根因。[事实 + 推断]

任务书中长对话 30–44% jank 来自较早的 debug 版本，且新增的增量映射和 Markdown 缓存尚未可靠复测。因此，不能据此认定 Flutter、React Native 或 KMP 会明显更流畅。

将现有约 9,200 行主代码整体迁移至新框架，会同时增加 SSH、安全、后台执行和 UI 性能方面的回归风险。

## 总体方案取舍

| 决策   | 方案 A      | 方案 B           | 方案 C          | 推荐           |
| ---- | --------- | -------------- | ------------- | ------------ |
| 交互   | 状态看板      | 待办收件箱          | 会话列表          | B + Agent 总览 |
| 客户端  | Kotlin 原生 | Flutter / RN   | KMP + 双端原生 UI | 先 A，预留 C     |
| 连接   | 纯 SSH     | 主机 Companion   | 云中继 + 推送      | 先 B，逐步扩展 C   |
| 对话数据 | JSONL 轮询  | 统一事件抽象 + 增量传输  | 全面迁移 ACP      | B，兼容 A/C     |
| 审批   | 读屏发键      | 请求 ID 绑定的结构化审批 | 人工打开终端        | B，C 兜底       |
| 实施   | 全量重写      | 渐进重构           | 并行重新开发        | B，先新 UI 垂直切片 |

推荐不是成本最低的方案，而是我认为在一个人业余开发、AI coding agent 辅助实现、将来可能商业化这些条件下，风险与体验收益最均衡的方案。

## 建议的产品验收目标

以下是新方案的设计预算，不是现有性能，也不是竞品实测：

| 指标               | 建议目标                |
| ---------------- | ------------------- |
| 首屏缓存内容可见         | 温启动 P95 ≤ 300 ms    |
| 打开首页识别最高优先事项     | ≤ 3 s               |
| 处理一条简单结构化审批      | P95 ≤ 15 s（端到端人工操作） |
| 首页展示的 Agent 信息密度 | 首屏可扫视 3–5 条重要事项     |
| 进入已有会话           | 本地缓存可见 P95 ≤ 300 ms |
| 在线状态增量可见         | P95 ≤ 1 s（网络正常时）    |
| 120 Hz 单帧理论预算    | 8.33 ms             |
| 重复执行未知结果的写操作     | 0 次自动重发             |
| 结构化审批错绑请求        | 0 次（正确性门禁）          |

R0 最终推荐：先改变信息架构，再改造数据与连接架构，最后围绕真实测量结果做性能与视觉打磨。 不建议上来就用 Flutter 或 React Native 重写整个工程。

## R2.2 推荐的信息架构（IA）

```
Herdr Mobile
│
├── 待处理（默认首页）
│   ├── 需要我回答
│   ├── 需要审批
│   ├── 需要审阅
│   ├── 异常 / 未确认发送
│   └── 最近处理记录
│
├── Agent 总览
│   ├── 全部 / 关注
│   ├── 项目 / 主机筛选
│   ├── 工作中
│   ├── 已完成（默认收起）
│   ├── 空闲 / 未知
│   └── Agent 详情
│       ├── 对话
│       ├── 工具 / 文件 / Diff
│       └── 终端（兜底）
│
└── 设置（顶部头像或工具入口）
    ├── 主机和连接
    ├── 配对新主机
    ├── 通知
    ├── 安全与设备
    └── 诊断
```

底部只保留两个主要入口：

`待处理` 和 `全部 Agent`。

主机配置不应该继续占据主要底部导航。对日常用户来说，S6 是低频任务；把它留在一级导航，会浪费最宝贵的位置。

一个必要的状态模型变化 [推断]：

将两类数据彻底分开：

- `AgentState`：blocked / working / done / idle / unknown。
- `AttentionItem`：`permission_request`、`question`、`review_required`、`delivery_uncertain` 等具有明确生命周期的事项。

`blocked` 只能提示“可能需要你”，不能直接推导出一个可以安全执行的审批操作。没有结构化请求 ID，就没有真正的快捷审批。

## R2.3 S1–S7 点击路径与步骤

### 三种交互模型的任务成本

| 场景              | A 看板 | B Inbox | C 会话流 |
| --------------- | ---- | ------- | ----- |
| S1 看谁在等我        | 0    | 0       | 0–1   |
| S2 简单结构化回答      | 1–3  | 1–2     | 2–3   |
| S3 阅读某 Agent 进展 | 1    | 2       | 1     |
| S4 补充文字指令       | 2    | 3       | 2     |
| S5 从通知处理事项      | 1–3  | 1–2     | 2–3   |
| S6 进入主机添加       | 2–3  | 3       | 3     |
| S7 打开终端         | 2–3  | 4       | 3     |

[推断] 点击次数是原型流程预算，不是现有 App 实测。0 表示打开首页后无需额外点击；不计解锁、启动 App、键盘输入和系统授权弹窗。长按计一次操作。

### 推荐方案 B 的完整路径

| 场景       | 路径                              | 操作数         |
| -------- | ------------------------------- | ----------- |
| S1       | 打开 App → 自动显示待处理事项              | 0           |
| S2 简单选择  | Inbox → 点击绑定到请求的选项 → 确认回执       | 1–2         |
| S2 高风险审批 | Inbox → 事项详情 → 阅读命令/风险 → 长按确认   | 2–3         |
| S3       | Inbox → 全部 Agent → 目标 Agent     | 2           |
| S4       | 全部 Agent → 目标 Agent → 输入文字 → 发送 | 3，不计输入      |
| S5       | 点击通知 → 指定事项 → 处理                | 2，若需详情则增加 1 |
| S6       | 设置 → 主机 → 添加主机                  | 3，不计配对步骤    |
| S7       | 全部 Agent → Agent → 更多 → 终端      | 4；接管需额外确认   |

这里有一个权衡：S3/S4 比当前看板方案多一步。

我的解决办法不是改变首页，而是提供两个加速入口：最近使用的 Agent 和可配置的关注 Agent。它们不改变全局 IA，但能让高频编辑会话从 2 次点击降为 1 次。

## R2.4 一个 Agent 行在 3 秒内必须表达什么？

我建议每个 Agent 行只回答四个问题：

1. 是谁？ Agent 名称、易识别的项目名称。
2. 现在什么状态？ 等待、运行、完成、未知。
3. 与我有什么关系？ 需要回答什么、执行什么决定、是否有未读成果。
4. 这个判断可靠吗？ 最后确认时间、当前是否在线。

信息优先级：

| 层级 | 信息                       | 位置      |
| -- | ------------------------ | ------- |
| P0 | 待处理请求类型与正文摘要             | 主标题     |
| P0 | Agent / 项目               | 次标题     |
| P0 | 是否可安全操作                  | 行动区     |
| P1 | 等待时长                     | 右侧或摘要下方 |
| P1 | 最新确认时间                   | 小型状态标识  |
| P2 | Host / Workspace         | 详情或筛选器  |
| P3 | tab、pane_id、cwd、revision | 技术信息页   |

等待时长必须有可信来源。

目前 Herdr 的 `blocked` 状态不等于已经提供 `blocked_since` 时间戳。你在 §3 描述的是状态事件与快照，并未确认持久等待时间接口。

建议对比：

| 方案                       | 可靠性    | 代价        |
| ------------------------ | ------ | --------- |
| A. 客户端收到 blocked 时开始计时   | 断线后不可靠 | 最容易做      |
| B. Companion 持久化状态切换事件时间 | 更可靠    | 需要新增事件存储  |
| C. 从 JSONL / 终端推算        | 容易误判   | 不推荐用于正式时长 |

推荐 B，A 作为降级。

例如：

- 已确认时间：`等待 4 分钟`
- 仅当前连接发现：`正在等待 · 起始时间未知`
- 断线缓存：`上次看到等待中 · 8 分钟前同步`
- 数据不一致：`状态待确认`

不应该因为客户端刚启动，就把一个可能等了 40 分钟的 Agent 显示为“刚刚开始等待”。

## R2.5 S2：回答与审批是否可以不进对话？

可以，但必须根据请求的结构化程度决定交互方式。

### 三种方案

| 方式         | 优势          | 风险         | 适用       |
| ---------- | ----------- | ---------- | -------- |
| A. 列表内联按钮  | 最少点击        | 容易误触、上下文不足 | 简单结构化选择  |
| B. 底部详情弹层  | 单手可操作、上下文更全 | 多一步        | 默认推荐     |
| C. 完整对话内处理 | 信息最充分       | 操作较慢       | 高风险、复杂回答 |

我建议建立严格的准入条件。

允许快捷处理

请求拥有稳定 `request_id`，选项和操作内容完整，服务端支持绑定该 ID 的一次性回应，且目标权限仍有效。

必须展开完整上下文

删除文件、覆盖代码、修改生产数据库、网络公开、权限永久放行、执行未知脚本等操作。展示命令、工作目录、影响范围和实际授予的权限。

不提供快捷批准

只有读屏推断，只有 `blocked` 状态，没有请求 ID，无法验证操作是否仍对应同一请求，或不能确认对端是否接收时。

长按 700–900 ms、震动反馈、按钮防重复点击可以作为防误触措施，但不能作为并发安全保证。

发送前还必须满足：

`request_id` 相同、请求仍处于待处理状态、回答仅能被目标请求消费，以及服务端能明确区分已接受、已拒绝和结果未知。

如果提供者没有这些保证，显示“查看终端 / 手工处理”，而不是提供带误导性的批准按钮。

## R2.6 多主机、多会话和团队

这里不应该先按主机分组。

| 方案                        | 优点     | 缺点             |
| ------------------------- | ------ | -------------- |
| A. Host → Session → Agent | 结构准确   | 层级过深           |
| B. 全局 Agent 聚合 + Host 筛选  | 快速发现问题 | 需要稳定跨主机 ID     |
| C. 按人员 / 团队分组             | 适合协作   | 需要可靠的用户归属与权限系统 |

推荐 B，未来再加入 C。

建议默认展示全局待办，支持按项目、主机过滤。可提供“关注的 Agent”，但不要立即把它命名为“只看我的”。

因为当前 Herdr 层级并没有证明存在可信的 Agent 所有权字段。

团队其他人正在电脑上操作同一个 pane 时，需要区分：

- 确知有人控制：由 Companion 的控制租约 / Presence 提供，显示“其他设备正在操作”。
- 只知道其他端可能操作：显示“此会话可能已被其他端更新”，绝不能虚构在线人员。
- 确知已失去控制权：停止或禁用相关发送，明确告知。

我推荐 Companion 未来提供 `device_id`、`actor_id`、控制权状态与审计记录。光靠手机 App 轮询无法可靠获得多人协作事实。

## R2.8 输入与发送模型

### 输入控件的取舍

| 方案                           | 优势     | 问题       |
| ---------------------------- | ------ | -------- |
| A. 简单文字输入                    | 稳定易用   | 多模态能力弱   |
| B. 扩展型 Composer（文字、语音、附件、引用） | 统一交互入口 | 实现成本更高   |
| C. 命令优先输入栏                   | 专业、高效  | 手机上学习成本高 |

推荐 B，渐进启用。

具体规则建议：

- 普通输入：1–5 行，长文本展开编辑器。
- 语音：只有识别功能真实可用后才显示，转写先进输入栏，用户审阅后发送。
- 图片：只有当前 Agent 与传输通道支持附件时才可用。
- 快捷回复：优先提供“继续”“运行测试”“检查改动”等可编辑建议，不自动发送。
- Slash 命令：由当前 Agent 的能力清单确定，不假设所有 Agent 支持相同命令。
- 引用：引用某条消息或 diff 时，保留 `message_id` 与行范围，避免只能复制大段文本。

### 写操作状态：建议比现有三态更细

提交前

草稿

进入发送队列

待发送

已发出请求

发送中

对端确认接收

已接收

对端明确拒绝

已拒绝

未得到确定结果

结果未知

[推断] 推荐用显式回执实现以上状态。“已接收”不是“已执行成功”，更不是“Agent 已完成”。

如果远端在客户端超时前可能已经执行了命令，而请求缺乏幂等能力，就进入“结果未知”，不自动重发。

未知态文案应该是：

“可能已经送达。请先查看 Agent 的最新输出或向主机查询执行记录，再决定是否重新发送。”

## R2.9 连接与数据新鲜度

我建议分别建模，而不是一个 `Connected` 布尔值控制所有 UI。

### 连接状态

| 状态           | 文案     | 可执行动作     |
| ------------ | ------ | --------- |
| Online       | 已连接    | 查看连接详情    |
| Reconnecting | 正在恢复连接 | 查看缓存、手动重试 |
| Offline      | 已离线    | 重连        |
| AuthRequired | 需要重新验证 | 重新认证      |
| Untrusted    | 主机身份变化 | 停止连接、核对指纹 |

### 数据状态

| 状态       | 文案            |
| -------- | ------------- |
| Verified | 已确认状态 · 时间    |
| Cached   | 缓存状态 · 上次同步时间 |
| Unknown  | 目前无法确认        |

同一台手机可以处于 `Online + Cached`：SSH 已连接，但某个 Agent 的快照尚未成功对账。

反过来，连接断开后仍能读取之前的消息，但必须显示 `Offline + Cached`。

### 三种显示策略

| 方案                  | 优势      | 风险       |
| ------------------- | ------- | -------- |
| A. 每个组件放连接标签        | 信息准确    | UI 噪音高   |
| B. 全局连接摘要 + 事项局部新鲜度 | 兼顾准确与简洁 | 需要统一状态模型 |
| C. 只显示全局连接          | 最简洁     | 多主机时会误导  |

推荐 B。

对于每个可操作事项，必须保留局部新鲜度和当前请求是否仍有效的信息。

不能简单规定“5 秒内一律实时”；空闲 Agent 本来就可能长期不发事件。在线与可信新鲜度应由连接健康、快照确认、订阅连续性和事件丢失检测共同决定。

## R2.10 通知策略

### 三种路线

| 方案                     | 可靠性            | 部署成本 | 推荐阶段    |
| ---------------------- | -------------- | ---- | ------- |
| A. 本地通知 + 前台服务         | 受系统后台限制        | 低    | 兼容模式    |
| B. 主机 Companion + 推送服务 | 可在 App 进程退出后送达 | 中    | 目标方案    |
| C. 完整自建 E2EE 云中继       | 跨网络能力最完整       | 高    | 商业化阶段评估 |

### 通知分级

| 事件             | 建议              |
| -------------- | --------------- |
| 结构化审批待处理       | 高优先级            |
| Agent 明确要求用户回答 | 高优先级            |
| 长任务完成、等待审阅     | 普通通知，可按项目设置     |
| 关键执行失败         | 普通或高优先级，取决于配置   |
| 正常工具调用         | 不通知             |
| 普通流式消息         | 不通知             |
| 短暂重连           | 默认静默            |
| 持续离线           | App 内提示，必要时合并通知 |

通知点击必须落到具体事项，而不是只打开首页。

推荐深链目标包含稳定的主机、Session、Agent 和 `AttentionItem` 标识。打开后重新校验请求是否仍有效；如果其他人已处理，则展示“此事项已解决”，而不是留下可点击的旧审批按钮。

锁屏默认只显示：

“有 1 个 Agent 需要你处理。”

不展示命令、仓库绝对路径、主机地址、访问密钥或详细 Prompt。

首次配置时，不要一启动就索要通知、后台、自启动、电池优化等所有权限。建议在用户首次看到一个真实 Agent 后，先说明“开启通知可在 Agent 等待时提醒你”，再请求系统授权；厂家特殊限制放到诊断页按需引导。

一个需要明确的事实修正：任务书 §3.4 的 Android 15 `dataSync` 6 小时限制有适用条件——官方规定针对 Android 15 及以上系统中、目标 SDK 为 35 及以上的相关类型前台服务；并非所有 Android 前台服务无条件统一限制 6 小时。

## R2.11 首次配置与配对

目前手工输入主机、端口、密钥、指纹、Herdr 路径和 Session 的流程过长。

### 三种方案

| 方案                 | 用户操作            | 代价               | 推荐   |
| ------------------ | --------------- | ---------------- | ---- |
| A. 保留手动 SSH 配置     | 约 6–10 个输入/确认环节 | 零服务端依赖           | 高级入口 |
| B. 主机一条安装命令 + 手机扫码 | 约 3–5 次确认操作     | 要部署 Companion    | 默认   |
| C. 账号登录 + 自动发现电脑   | 约 2–4 步         | 需账户、Relay、设备授权服务 | 后期   |

这些步骤数属于建议交互预算，并非竞品实测。

我建议首选 B，保留 A。

目标流程：

```
电脑
  安装 Herdr Companion
     ↓
  生成一次性配对邀请
     ↓
  显示 QR（短时有效）

手机
  打开 Herdr Mobile
     ↓
  扫码
     ↓
  核对主机身份与访问权限
     ↓
  建立加密连接
     ↓
  读取首个 Snapshot
     ↓
  显示 Agent 列表
```

关键安全规则：

二维码只能包含一次性邀请、服务定位信息、设备配对材料或经过保护的主机身份信息，不能包含主机 SSH 私钥。

如果通过可信的主机终端显示二维码，可以把 SSH host key fingerprint 作为带外配对材料；如果二维码来自不可信渠道，仍需独立核验主机身份。不能因为“扫过二维码”就静默信任任意服务器。

这个方向有真实参考：0cv 的 Herdr Mobile Relay 已经公开使用主机安装、打印 QR、手机扫码进入的流程；Happy 也提供一次配对后跨设备使用的模式。

## R2.13 产品模型的最终推荐

对信息架构，我建议正式冻结以下原则，再进入 R3 的具体屏幕设计：

| 决策项  | 推荐                            |
| ---- | ----------------------------- |
| 首屏主体 | `AttentionItem`，而非 Agent 状态列表 |
| 第二入口 | 全部 Agent，总览真实运行状态             |
| 主机组织 | 全局聚合 + 筛选                     |
| 对话   | 结构化阅读优先，原始内容可追溯               |
| 审批   | 有请求 ID 与原子回应能力才快捷执行           |
| 输入   | 文字优先，语音与附件按真实能力渐进启用           |
| 新鲜度  | 连接、数据、操作回执三者独立                |
| 通知   | 具体事项深链，默认隐藏敏感信息               |
| 配对   | Companion + 一次性扫码，保留 SSH 手工模式 |
| 大屏   | 自适应列表详情双栏                     |

### 需要原型或真机验证的五个核心假设

这些不是已证实的结论，不能直接当作 UX 事实：

1. Inbox 比当前看板能更快帮助用户找到最高优先级待办。
2. 用户在首页使用底部弹层，能比进入对话更快、安全地完成简单回复。
3. 多 Agent 情况下，全局聚合比按主机分类更容易理解。
4. 结构化重点阅读比完整转录更适合 500–2000 条消息。
5. 两个底部入口足以覆盖 S1–S7，不会让 S3/S4 的增加步骤成为主要体验退化。

建议用同一组真实任务让 3–5 名开发者测试两个可点击原型，分别记录首次正确识别时间、任务完成时间、点击次数、误操作次数和主观工作负担。这个样本量只能用于发现明显的可用性问题，不能据此证明总体统计优势。

最后一个重要判断： 如果后续证实 Herdr 的结构化 `AttentionItem` 很难稳定从现有协议与 Agent 适配器获得，就必须允许部分条目降级为“待检查的 Agent”，而不是为了保持漂亮的 Inbox 形式而虚构审批结构。

这既是信息架构决定，也是协议与安全架构的约束。

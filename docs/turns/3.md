Herdr Mobile 全面重构调研报告
第四部分 · 2026-11-02 · R9–R10：迁移路线、事实复核与遗漏风险

这一部分完成任务书最后两项交付物，并对 R0–R8 的架构建议进行最后一次风险审查。

先给出阶段性结论：[推断] 我不建议从零重写 Herdr Android，也不建议先开发完整 Companion。

当前项目约 9,200 行主代码、2,400 行测试，虽然 UI 和分层存在明显问题，但已经积累了不少有价值的协议兼容、安全与状态恢复逻辑。直接重写容易把这些经验一起丢掉。

更合理的做法是：保留旧版作为可靠底座，在同一个项目中渐进替换 UI 和架构，同时以独立实验验证 Companion。

R10.2 P0：Claude PermissionRequest Hook 不自动提供稳定请求 ID
这是本轮最重要的新发现，也是对前面 R2、R5、R7 一个隐含前提的修正。

[官方事实] Claude Code 当前 Hooks 文档明确写明，PermissionRequest 输入包含 tool_name 和 tool_input，但是不包含 tool_use_id。

官方同时说明，如果 PermissionRequest Hook 与 SDK 的权限回调等机制同时参与，先作出有效决策的一方可能生效。

Claude Code Docs

这意味着：

不能仅因为某条审批来自 PermissionRequest Hook，就认定它已经具备可靠的一次性请求身份和完整的竞态防护。
三种审批实现路线
方案	请求关联	竞态风险	推荐
A. 继续 Hook 文件 IPC，按会话 + 命令内容关联	弱	高	不用于快捷批准
B. 自建 Hook Broker，持有每次待决 Hook 调用	可以建立 Broker 本地请求 ID	仍需处理超时、其他决策源和失效	Claude TUI 的优先研究方案
C. 使用 ACP / SDK 的真正请求-响应通道	更明确的请求身份	需要托管相应 Agent 会话	适合新会话模式

推荐 B 作为当前 TUI 模式的研究方向，同时承认它不天然等价于 ACP 的原子审批机制。

Broker 至少必须保存：

broker_request_id / session_id / tool_name / tool_input / hook_generation / deadline / pending_state / resolved_state

还要验证 Hook 调用生命周期中，手机的回应是否仍能绑定到原始待决调用，以及超时或其他端已经响应时会发生什么。

如果无法证明，就只展示“需要手工确认”，不提供快捷批准。

这也意味着原先提出的“同一个请求 ID + 一次性响应即可安全”仍不够精确：请求 ID 必须属于真正负责消费该回应的权限协议，或由能够维持原始待决调用生命周期的 Broker 安全映射。

相比之下，ACP 的 session/request_permission 是 JSON-RPC 请求，具有明确的请求与响应对应关系，也规定了取消时如何返回取消结果。

R10.3 P0：Companion 的事件日志不能修复 Herdr 已经丢失的历史事件

[官方事实] Herdr 官方明确表示：
- 原始事件历史不持久。
- events_lost 会导致订阅关闭。
- Snapshot 与事件没有共同的序列边界。
- 恢复只能取得当前权威状态，不能找回所有遗漏的历史事件。

这意味着，如果 Companion 已经停止运行 30 分钟，那么重新启动后不可能单凭 Herdr Snapshot 恢复那 30 分钟所有 Agent 状态切换。
三种事件一致性方案
方案	恢复能力	代价
A. 仅 Snapshot	恢复当前状态	低
B. Companion 记录自己观察到的事件 + Snapshot	恢复已持久化的历史，缺口明确标记	推荐
C. 改造 Herdr 或 Provider，提供可靠持久事件源	最完整	高，涉及上游维护

推荐 B，不能承诺不存在历史缺口。

需要两个不同的概念：

CurrentState 表示“现在是什么”；EventHistory 表示“过去发生过什么”。

如果 Companion 中断，当前状态可以重新核验，但等待时长、历史状态切换和通知记录可能出现不可恢复的缺口。

[推断] UI 必须能够显示“当前状态已确认，但部分历史事件缺失”，而不是把这两个概念合并为一个 Fresh 标签。

这也影响 R2 中“等待 4 分钟”的准确性。若状态切换时间只能从缺失的事件历史中推算，应显示“等待开始时间未知”。

R10.6 P1：多主机身份与 Agent 身份需要更严格的定义

A. 只用 pane_id	低	跨主机冲突

- HostIdentity：可信主机身份。
- RuntimeSessionKey：Herdr 会话。

最终决策：R0–R10 收束
经过四轮分析，我对最初 R0 的推荐总体保持不变，但补充了两个重要前置条件：
1. Companion 不应直接进入正式开发。 必须先研究 Herdr 已有的远程 Endpoint 和 capability negotiation，确认是否值得复用。
2. 结构化审批不能简单等同于 Claude PermissionRequest Hook。 需要先确认真正的请求关联与有效性语义，否则只能做安全的只读待处理提示。

我认为应该真正优先执行的三件事

第一：建立可信的性能与安全基线

完成 M0。尤其是当前 Release 长对话表现、R8 能否安全开启、WriteLedger 和指纹验证的回归。




第二：尽快完成一条全新 UI 垂直切片

做 M1：Attention Inbox → Agent 详情 → 安全的只读或结构化处理入口。让真实用户在设备上比较，而不是继续只讨论抽象设计。




第三：单独立项验证 Companion 和审批协议

先做只读主机聚合与事件恢复，确认不会破坏现有 Herdr TUI，再探索能够安全处理审批的 Provider 通道。




调研的最终结论
Herdr Mobile 最有价值的竞争优势，不是让手机也能使用终端，而是让用户在离开电脑后，仍能安全、迅速地推进正在等待自己的 Agent。

从这个目标出发，三个判断最值得坚持：

第一，重新设计首页是必要的，但不能将 blocked 状态伪装成安全可执行的审批。 Attention Inbox 必须建立在可信的数据与请求生命周期上。

第二，连接架构需要改变，但不需要重造 Herdr。 充分利用 Herdr 正式能力，再用轻量 Companion 补足转录、增量、设备权限和推送。

第三，当前没有足够证据支持全面更换 Compose。 真正可靠的性能基线、分层和大消息渲染优化应优先于框架迁移。

至此，R0–R10 全部交付完成。它们可以作为重构方案讨论和工程任务拆分的研究依据，但还不是经过仓库代码审查、协议实测、视觉原型验收后冻结的最终实施规格。

我建议下一步从 M0 性能与安全基线任务书及 M1 新版交互原型规格开始，严格保持小里程碑、可验证、可回滚，并在正式设计冻结前不向本地 Agent 下发大规模重写任务。

# Herdr Mobile 全面重构调研报告

第三部分 · 2026-11-02 · R6–R8：动效、系统架构与性能工程

本轮继续严格对应任务书 §0.2 的 R6、R7、R8，重点回答 §5.B 的问题 11–17、§5.C 的问题 18–21，以及 §5.D 的动效问题。

先给出一个会影响全部工程决策的判断：

Herdr 当前需要的不是更多动画，而是把“正确的业务状态、即时的本地反馈、可控的计算成本”结合起来。

根据任务书，你的 500 条长对话曾测得 30–44% jank，但测量发生在较早的 debug 构建，后来增加的增量映射、Markdown 缓存等优化尚未可靠复测。因此，这个数字证明存在严重的历史性能问题，却不能证明 Compose 是根因，也不能代表 0.1.1 Release 的当前性能。

[事实] 120 Hz 的刷新周期为 `1000 / 120 = 8.333 ms`。但这不意味着 App 主线程可以占满 8.33 ms：系统调度、RenderThread、GPU、合成与显示截止时间都需要余量。

[推断] 推荐用以下内部工程预算指导实现：

| 工作阶段                     | 120 Hz 建议预算 |
| ------------------------ | ----------- |
| 主线程状态读取、Composition      | ≤ 1.5 ms    |
| Measure / Layout         | ≤ 1.5 ms    |
| UI 绘制准备及提交               | ≤ 1.0 ms    |
| RenderThread、GPU 与剩余管线余量 | 约 4.3 ms    |
| 单帧总周期                    | 8.33 ms     |

这些不是 Android 官方规定的固定分配，也不能简单把各阶段耗时相加作为最终 Jank 判断。实际验收必须使用 FrameTimeline 的 deadline/overrun 和真实显示帧。

Android 官方建议用 Release + R8、Baseline Profiles、Perfetto 等测量真实性能，并特别强调 Lazy 布局的稳定 key、`contentType` 和降低无效重组。

## R6.2 三种动效策略

| 方案                   | 体验          | 性能风险 | 工作量 |
| -------------------- | ----------- | ---- | --- |
| A. 基本使用系统默认          | 一致、稳定，但可能平淡 | 低    | 低   |
| B. 精选少量有意义的转场与微交互    | 精致、有反馈、容易维护 | 可控   | 中   |
| C. 大量共享元素、模糊、弹簧及动态背景 | 展示效果强       | 高    | 高   |

推荐 B。

Warm Ledger 不应该是炫技型设计语言。它应该在操作发生时明确、优雅地回应；在用户阅读代码或长对话时，尽量保持安静。

统一使用三类 Easing：

- E1 / Standard：`cubic-bezier(0.4, 0, 0.2, 1)`，一般状态变化。

| 动效场景          | 时长         | 曲线    | 实现策略            | 降级       |
| ------------- | ---------- | ----- | --------------- | -------- |
| 按钮按下          | 70–100 ms  | E1    | 颜色或轻微透明度        | 直接切状态    |
| 列表新增事项        | 160–200 ms | E2    | 透明度 + 少量平移      | 仅淡入或直接出现 |
| 列表删除事项        | 120–160 ms | E3    | 淡出后移除           | 直接移除     |
| Agent 状态变更    | 120–180 ms | E1    | 状态标识交叉淡入淡出      | 立即切换     |
| Attention 卡展开 | 180–240 ms | E1    | 内容显隐，避免大范围连续重排  | 直接展开     |
| 发送按钮状态变化      | 100–160 ms | E1    | 图标 / 状态切换       | 静态状态     |
| 发送被远端接收       | 120–180 ms | E2    | 一次性回执反馈         | 文字回执     |
| 新消息到达         | 120–180 ms | E2    | 可见新消息淡入         | 直接显示     |
| 底部 Sheet 进入   | 220–280 ms | E2    | Y 平移 + Scrim    | 无动画打开    |
| 底部 Sheet 退出   | 160–220 ms | E3    | Y 平移 + Scrim    | 无动画关闭    |
| 页面前进          | 180–240 ms | E1    | 轻微位移 / 淡入淡出     | 直接切换     |
| 页面返回          | 手势驱动       | 随手势进度 | Predictive Back | 系统默认     |
| 连接重试          | 不设连续循环     | —     | 静态状态 + 时间变化     | 静态       |
| 网络错误反馈        | 120–180 ms | E1    | 内联错误显现          | 立即显示     |

### 两个需要特别处理的交互

第一，列表插入并非总要动画。

如果 20 个 Agent 同时发生状态更新，不应该连续播放 20 组插入、移动与淡出动画。建议只有用户可见区内、由一次明确事件触发的少量结构变化才启用动画；批量对账则一次性切换。

第二，发送不使用“发送成功”的假动画。

可以在用户点击后立即从“草稿”切为“发送中”，但成功视觉反馈必须等待真实的服务端或 provider 回执。

当前网络 P50 为 300–500 ms，这段时间应显示可靠的过程状态，而不是提前播放完成动画。

## R6.4 Predictive Back 的正式策略

[事实] Android 目前支持系统预测性返回动画；官方文档指出，使用支持的 Navigation API 更容易接入，Navigation Compose 从 2.8.0 起支持相关行为。根 Activity 错误截获 Back 可能阻止系统返回动画。

Android Developers



对比：

| 方案                    | 优点     | 代价         |
| --------------------- | ------ | ---------- |
| A. 全部交给系统和 Navigation | 简单、可预期 | 自定义程度有限    |
| B. 在导航框架内定义少量页面转场     | 控制品牌体验 | 需要测试返回栈和手势 |
| C. 自写全套返回手势与转场        | 自由度高   | 兼容成本和错误风险高 |

推荐 B，但保留 A 作为默认和回退。

- Inbox → Agent：可以使用轻微横向位移。
- Agent → Diff：可以使用小幅淡入。
- 全屏审批 → 返回：优先使用系统返回与正确的弹层关闭语义。
- 手势进行中，动画进度必须跟随用户手势，不应再单独启动固定 220 ms 的动画。
- 用户取消返回手势时，保持原页面和当前草稿，不触发业务提交。

不推荐首版使用复杂的 Shared Element 转场把 Agent 卡片变形为整个长对话页。收益有限，却会扩大与长列表、键盘和网络状态之间的耦合。

## R6.5 120 Hz 下哪些效果应该砍掉？

这里区分现在应当禁用与并非技术上绝对不可能实现。

| 视觉效果              | 本轮决策 | 原因               |
| ----------------- | ---- | ---------------- |
| 长列表每条消息持续呼吸动画     | 砍掉   | 无业务价值，长期占用帧时间    |
| 流式文本每个 token 淡入   | 砍掉   | 高频重组、增加阅读干扰      |
| 所有 Agent 状态标识持续脉冲 | 砍掉   | 信息噪音、无障碍与耗电问题    |
| 滚动列表上大面积动态模糊      | 砍掉   | GPU/合成风险，不值得优先投入 |
| 长工具输出逐行展开动画       | 砍掉   | 大量布局变化           |
| 所有列表项使用复杂动态阴影     | 砍掉   | 收益有限，先验证基线       |
| 新消息轻微淡入           | 保留   | 可局部实现            |
| 底部 Sheet 平移       | 保留   | 有明确空间语义          |
| 简单交叉淡入淡出          | 保留   | 成本可控             |
| 状态颜色切换            | 保留   | 直观、可局部更新         |
| 预测性返回             | 保留   | 平台原生体验           |

Compose 官方性能资料建议，将 `alpha`、位移等动态属性尽可能推迟到 Draw/Layout 阶段读取，避免每帧驱动不必要的 Composition。

## R6.6 低功耗、减少动画与高刷新率降级

建议定义三档动效模式：

| 模式           | 条件                   | 行为             |
| ------------ | -------------------- | -------------- |
| Full         | 正常设置、性能达标            | 标准动效           |
| Reduced      | 系统减少动画、动画时长关闭或用户主动选择 | 直接切状态，保留静态反馈   |
| Conservative | 省电模式或长列表性能持续超预算      | 禁用非必要动画、减少装饰效果 |

注意：[推断] Android 各版本并没有一个可以简单等同于所有平台“Reduce Motion”的统一业务开关。需要读取当前系统动画设置，结合无障碍与省电策略正确实现，不能凭一个不存在的通用 API 假定全部设备行为一致。

动态降级不建议用“用户连续滑动时检测到卡顿就实时关闭全部动画”的简单做法，因为这可能导致视觉反复变化。更合理的是在页面级预先决定模式，或由用户设置显式控制。

## R6.7 R6 验收指标

我建议分为硬性正确性要求和性能目标。

| 项目                   | 推荐通过线                             |
| -------------------- | --------------------------------- |
| 发送成功动效               | 只能由可信回执触发                         |
| 减少动画                 | 业务反馈与焦点语义不丢失                      |
| 120 Hz 页面转场          | JankStats jank ≤ 3%（目标）           |
| 120 Hz 静态页面滚动        | JankStats jank ≤ 1%（目标）           |
| 120 Hz 长对话滚动         | jank ≤ 5%（阶段门槛），最终争取 ≤ 2%         |
| 120 Hz FrameTimeline | P95 frame overrun ≤ 0 ms（目标）      |
| 动画期间                 | 不执行 JSONL 大文件解析、Git diff 计算或同步 IO |
| 输入、返回、滚动             | 不发生卡住、丢失草稿或错误触发操作                 |

这里的 jank 率是项目自定门槛，不是 Google 规定的统一行业标准。FrameTimeline 的 `frameOverrun` 与 UI 线程耗时也不是同一个概念，必须分开记录。

JankStats 可提供每帧是否 jank、UI 帧耗时，以及 Android 12+ 上的 frame overrun 信息；这些可以作为 MIUI 真机 Macrobenchmark 不可用时的应用内测量基础。

# R7｜系统架构：客户端、连接、数据源、安全与测试

## R7.1 首先明确：架构必须保留的产品边界

R0 推荐引入主机 Companion，但这并不意味着应该另写一个 Agent Runtime。

Herdr 仍然负责 PTY、pane、session、Agent 生命周期和终端控制；Companion 负责把这些能力转换成适合移动端消费的服务。

这一区分很重要。

如果 Companion 同时开始管理模型上下文、执行 Agent loop、替代 Claude/Pi 的交互模式，那么你实际上会从“Herdr 手机客户端”转向“新 Agent 平台”，项目范围将大幅增加。

### 推荐的三层边界

Mobile Client

UI · 本地缓存 · 发送账本 · 本地凭证

Herdr Companion

聚合 · 适配 · 事件增量 · 授权 · 推送

Herdr Runtime

Session / Pane / PTY

Agent Providers

Claude / Pi / Codex

[推断] 这是目标架构，不是当前已有组件。

## R7.2 客户端技术栈：比较六种路线

### 可核实的技术事实

Kotlin Multiplatform 的核心 Android/iOS 支持已经是 Stable，Compose Multiplatform 的 iOS UI 支持也被 JetBrains 标为 Stable。因此不能继续把“Compose iOS 不成熟”当作否定 KMP 的普遍理由。

Kotlin Multiplatform Documentation



React Native New Architecture 引入 Fabric、新线程与布局模型；Flutter 官方提供独立的渲染性能分析工具。这些框架都具备打造优秀移动 UI 的能力。

但这些文档没有证明 Flutter、RN 或 Compose 在 Herdr 的 2,000 条混合富文本消息场景下哪个更快。这个结论只能来自相同负载的对照实验。

### 六种客户端技术路线

| 方案                                 | Android 性能潜力 | iOS 复用  | SSH/系统集成  | 迁移代价 | 个人维护 |
| ---------------------------------- | ------------ | ------- | --------- | ---- | ---- |
| A. Kotlin + Compose                | 高            | 无       | 现有代码可用    | 低    | 较低   |
| B. KMP + Compose Multiplatform     | 高，需实测        | UI + 逻辑 | 平台适配仍需要   | 中–高  | 中    |
| C. KMP 共享核心 + SwiftUI              | 高，需实测        | 业务逻辑    | 各端原生      | 高    | 中–高  |
| D. Flutter                         | 高，需实测        | UI + 逻辑 | SSH、通知需适配 | 高    | 中    |
| E. React Native New Architecture   | 高，需实测        | UI + 逻辑 | 依赖原生模块    | 高    | 中–高  |
| F. Android Kotlin + iOS Swift 独立实现 | 高，需实测        | 协议可共享   | 原生集成好     | 最高   | 高    |

这是定性工程评估，不是已测的性能排名。

### 三个值得认真考虑的方案

方案 A：维持 Kotlin 原生，只重构内部架构

优点是保留已有 Android SSH 兼容经验、Room 数据、Compose UI 代码与真机调试手段。对于目前仅约 9,200 行的主代码，彻底调整 UI 和模块边界是可行的。

代价是未来推出 iOS 时需要建立新的 UI 与部分平台实现。

方案 B：现在迁移至 KMP + Compose Multiplatform

长期共享程度较高，Android 与 iOS 的设计组件可以使用同一套代码。

但现有 `sshj`、Android Keystore、Room 平台适配、通知、后台服务都不能简单假设可以直接编译到 iOS。跨平台必须重新设计 `expect/actual` 或接口隔离；Markdown、键盘、文本选择和滚动也需要双平台测试。

方案 C：KMP 共享领域核心 + 双端原生 UI

适合未来对 Android、iOS 的平台完成度都有很高要求的产品。共享事件协议、状态机、适配器模型，界面分别使用 Compose 与 SwiftUI。

代价是 UI 维护两份，而且 AI coding agent 必须同时掌握两个平台的设计与测试体系。

### 推荐结果

现在选 A，架构边界按 C 的思路设计。

重点不是立刻把每个 Gradle 模块都改成 `commonMain`，而是先确保领域模型不依赖 Android SDK：

```
interface SessionRepository {
    fun observeAgents(): Flow<List<AgentRecord>>
    fun observeTranscript(session: SessionKey): Flow<TranscriptPage>
}

interface RemoteTransport {
    suspend fun connect(endpoint: Endpoint): ConnectionResult
    fun events(): Flow<RemoteEvent>
    suspend fun request(request: RemoteRequest): RemoteResult
}
```

这些是抽象接口草案，不应直接作为定稿代码复制。真实实现还需要取消语义、数据新鲜度、流事件游标、错误类型及写操作生命周期。

什么时候推翻这个推荐？

如果你决定在近期同时正式发布 Android 和 iOS，并且愿意为此承担更多开发和维护成本，那么 KMP + SwiftUI/Compose 的共享核心方案值得立即进入对照原型。

[待实测] 三种技术栈各实现同一条 500 条混合内容会话，使用相同数据与设备条件进行测量；只有真实收益足以覆盖迁移成本时才切换。

## R7.3 连接架构：A、B、C 三条路线

### 方案 A：纯 SSH 优化

```
Android App
   │
   └── SSH persistent connection
         ├── events.subscribe
         ├── request channel / multiplex helper
         ├── SFTP transcript
         └── SFTP approval IPC
                 │
               Herdr
```

保留现有架构，只改进请求复用、channel 调度和轮询。

| 优点         | 缺点                      |
| ---------- | ----------------------- |
| 无需新增主机服务   | 会话文件和审批仍需轮询             |
| 安全信任边界相对熟悉 | 无真后台推送                  |
| 回归范围较小     | 每次请求与 SSH channel 机制强耦合 |
| 适合作为兼容模式   | 各种 provider 解析逻辑留在手机端   |

可以借鉴 tuan3w 的持久 SSH channel 主机脚本。它确实展示了减少反复 `exec` 的工程路径，但减少 channel 创建不等于能让网络 RTT 变成 0。

### 方案 B：主机侧 Companion

```
Android App
      │
      │ 1 条持久连接
      ▼
SSH tunnel / authenticated TLS
      │
      ▼
Herdr Companion
  ├── SessionAggregator
  ├── EventJournal
  ├── TranscriptTailer
  ├── ProviderAdapters
  ├── ApprovalBroker
  ├── WriteAudit
  └── PushNotifier (可选)
      │
      ├── Herdr Unix socket
      ├── Claude JSONL / hooks
      ├── Pi JSONL / RPC integration
      └── Codex app-server (可选)
```

Companion 不应持有用户的模型 API 密钥，也不应自行启动另一份未经允许的 Agent。

它优先连接已经存在的 Herdr 会话，读取其运行状态，并通过被授权的接口观察和操作。

### 方案 C：E2EE Relay + 推送

```
Mobile
  │
  ├── Direct connection (优先)
  │
  └── E2EE Relay
           │
           ▼
     Host Companion
           │
         Herdr

Host Companion ──▶ Push service
                        │
                        ▼
                     FCM/APNs
                        │
                        ▼
                      Mobile
```

它可以进一步解决跨 NAT 连接、移动网络变化、进程退出后的推送等问题，但需要额外的身份、密钥、Relay、推送与运维体系。

关键事实：Relay + TLS 并不自动等于端到端加密。 Relay 不可读取会话内容，需要独立设计端到端密钥协商、设备身份、消息加密、密钥轮换和撤销。

### 三方案取舍

| 指标     | A 纯 SSH    | B Companion     | C Companion + Relay |
| ------ | ---------- | --------------- | ------------------- |
| 部署复杂度  | 低          | 中               | 高                   |
| 主机侧进程  | 无          | 1 个             | 1 个                 |
| 跨网络连通  | 用户自己解决     | 用户自己解决          | 可由 Relay 协助         |
| 对话增量事件 | 仍需额外机制     | 可主动发送           | 可主动发送               |
| 结构化审批  | hook 文件轮询  | 可集中 Broker      | 可集中 Broker          |
| 后台真实推送 | 否          | 可选推送集成          | 完整目标能力              |
| 延迟上限   | 取决于 SSH/轮询 | 取决于网络及队列        | 加入 Relay 路径         |
| 安全实现范围 | SSH + 客户端  | SSH/设备鉴权 + 主机服务 | E2EE/设备/Relay/推送    |
| 运维成本   | 低          | 中               | 高                   |
| 对外收费扩展 | 受限         | 有基础             | 潜力最大                |

推荐 B 为主要产品架构，A 永久作为高级兼容模式，C 作为未来可选连接路径。

这里有一个有用的外部核查结果：

Herdr 官方 0.9.1 Socket API 文档已经描述了 `session.snapshot`、`events.subscribe` 的引导流程，且提到了客户端与服务器的 endpoint capability negotiation。说明上游在协议兼容性上有正式设计，不应永远依赖隐藏的 `remote-api-bridge` 作为唯一集成接口。

GitHub+1



但这不证明你当前设备上的 herdr 二进制已提供完全相同的接口。必须用你自己的 `herdr api schema --json`、版本号和一次实际握手确认。

## R7.4 Companion 的具体技术选择

| 方案                       | 开发效率 | 运行依赖       | 与 Herdr 集成          | 推荐   |
| ------------------------ | ---- | ---------- | ------------------- | ---- |
| A. Python 3 脚本           | 高    | Python 运行时 | Unix socket 易对接     | 快速验证 |
| B. Rust 单二进制             | 中    | 可避免外部语言运行时 | 与 Herdr 技术生态接近      | 长期推荐 |
| C. TypeScript + Bun/Node | 高    | 对应运行时或打包   | WebSocket/JSON 开发容易 | 可选   |

建议：先用 Rust 做架构设计；如果验证风险很高，用 Python 做小规模协议 Spike，而不是立即写完整 Python 服务。

目标 Companion 的最小职责只有六项：

1. 从 Herdr 读取快照与订阅事件。
2. 根据稳定游标增量读取对话。
3. 维护可恢复的统一事件序列。
4. 管理结构化请求的有效性与回执。
5. 暴露单条持久双向连接。
6. 保留最小审计和诊断信息。

不要第一版就加入用户账号、计费系统、复杂 Relay 和跨主机全局数据库。

## R7.5 Companion 的通信协议

建议采用 WebSocket + 版本化 JSON 消息，而不是让客户端直接消费多个上游格式。

### 三种协议选择

| 方案                           | 优点                | 问题                |
| ---------------------------- | ----------------- | ----------------- |
| A. NDJSON over SSH           | 实现直接              | 多平台复用、消息多路复用要自行处理 |
| B. WebSocket + JSON Envelope | 调试容易、持久双向、移动端生态成熟 | 需要明确重连与一致性        |
| C. gRPC Streaming            | 强类型、生成代码          | 初期引入成本较大          |

推荐 B。

一条连接承载状态、对话、审批及心跳。应用层包含：

```
{
  "version": 1,
  "messageId": "evt_1025",
  "stream": "transcript",
  "sessionKey": "hostA/session1/pane1",
  "sequence": 1025,
  "type": "message.delta",
  "payload": {}
}
```

这只是协议草案。

建议消息分成三类：

- `command`：客户端请求，带 `commandId`。
- `event`：主机发来的事件，带可恢复 `sequence`。
- `ack`：主机对接收或处理阶段的确认。

### 事件恢复语义

Companion 必须能应对断线、进程重启、重复事件和部分丢包。

推荐流程：

```
Mobile reconnect
      │
      ▼
发送 lastAppliedSequence
      │
      ├── Journal 仍有增量
      │       └── 回放缺失事件
      │
      └── Journal 不可恢复
              └── Snapshot + 新 epoch
                       │
                       ▼
                重建只读状态
                       │
                       ▼
                  恢复订阅
```

`sequence` 必须限定在某个具体 `epoch` 或 stream 内，不能跨主机重启盲目比较。

这里必须区分事件可靠性与写操作可靠性。

事件重复可以靠事件 ID 去重；但 `pane.send_keys` 或 `agent.prompt` 没有真正幂等支持时，不能把重复 `commandId` 直接当作可以安全重发的远程命令。

Companion 最多能防止自己重复派发已记录的命令，不能凭空证明 Provider 已经或尚未执行了某项操作。

## R7.6 对话数据源：JSONL、ACP、Codex、Claude SDK

这是我认为整个项目架构中最容易作出错误选择的地方。

### 先核实协议事实

ACP： 官方 v1 使用 JSON-RPC 2.0，提供 `session/prompt`、`session/update`、`session/request_permission`、ToolCall ID、取消等机制。它是 Agent 与客户端之间的交互协议。

[image](https://www.google.com/s2/favicons?domain=https://agentclientprotocol.com\&sz=32)

Agent Client Protocol+1



Codex app-server： 官方支持线程创建、恢复、流事件和服务端发起的审批请求，且区分命令审批、文件改动审批、网络权限等不同类型。

[image](https://www.google.com/s2/favicons?domain=https://developers.openai.com\&sz=32)

ChatGPT Learn+1



Claude Agent SDK： 官方 SDK 是用 Python/TypeScript 在自己的进程或应用中运行 Claude Code Agent 的集成方式；它不是天然连接到任意已经运行的 Claude Code TUI 进程的读取接口。

[image](https://www.google.com/s2/favicons?domain=https://platform.claude.com\&sz=32)

Claude Code Docs



Pi： 官方明确文档化 JSONL 会话树、JSON 流式事件和双向 RPC 模式；但 RPC 模式通常是针对以 RPC 模式运行并由调用者控制的 Pi 进程，不能假定可直接附着到现有 Herdr TUI。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+2



### 数据源取舍

| 数据源              | 结构化    | 实时增量    | 双向控制 | 能否直接观察当前 Herdr TUI  |
| ---------------- | ------ | ------- | ---- | ------------------- |
| Pi JSONL         | 是      | 文件新增可读取 | 否    | 通常可以，需定位文件          |
| Claude JSONL     | 是，内部格式 | 文件新增可读取 | 否    | 通常可以，需定位文件          |
| ACP              | 是      | 是       | 是    | 需要确认会话如何接入          |
| Codex app-server | 是      | 是       | 是    | 需要确认现有 Codex 会话如何接入 |
| Claude Agent SDK | 是      | 是       | 是    | 不能假定可无缝接管现有 TUI     |
| Herdr 屏幕输出       | 部分结构   | 可观察     | 可发输入 | 可观察，但不是可靠审批来源       |

### 三种数据架构

| 方案                                   | 优点            | 致命问题                    |
| ------------------------------------ | ------------- | ----------------------- |
| A. 继续统一 JSONL 解析                     | 不改变现有运行模式     | 非正式格式、审批不足              |
| B. 统一 `TranscriptEvent`，下挂多 Provider | 兼容现有工作流并可渐进增强 | 适配层设计有成本                |
| C. 全部 Agent 改用 ACP / app-server 启动   | 协议能力更统一       | 可能破坏你当前的 Herdr TUI 使用方式 |

推荐 B。

尤其不要为了获得 ACP 的一键审批，就要求用户把原本在 Herdr 里的 Claude/Pi 会话全部退出并重新启动。

这与你的产品核心目标矛盾：用户希望离开电脑后继续监督原来就在运行的会话。

### 能力等级：不要把所有 Provider 显示成一样

建议定义：

| 等级 | 能力              |
| -- | --------------- |
| L0 | 终端观察            |
| L1 | 结构化对话读取         |
| L2 | 发送文字与查看回执       |
| L3 | 结构化问答 / 权限审批    |
| L4 | 文件、diff、附件等高级能力 |

具体等级必须按当前会话和连接方式判断，而不是仅按 Provider 品牌判断。

例如，同一个 Claude Code：

- 普通 TUI + JSONL：可能是 L1/L2。
- 正确安装并验证 Hook Broker：可能具有 L3。
- 由支持对应协议的 SDK/ACP 方式托管：可能提供更完整的 L3/L4。

即使 Provider 文档中写着支持审批，如果当前会话不是通过对应协议接入，也不能启用那套审批能力。

## R7.7 统一 TranscriptEvent 抽象

建议规范为以下事件族，而不是直接设计一个容纳所有字段的巨型 `Message`：

```
sealed interface TranscriptEvent {
    val eventId: String
    val sessionKey: SessionKey
    val source: EventSource
    val observedAt: Instant
}

data class EventSource(
    val provider: String,
    val transport: String,
    val upstreamId: String?,
    val sourceRevision: String?
)

data class TextDelta(
    override val eventId: String,
    override val sessionKey: SessionKey,
    override val source: EventSource,
    override val observedAt: Instant,
    val messageId: String,
    val blockId: String,
    val delta: String
) : TranscriptEvent

data class MessageCompleted(
    override val eventId: String,
    override val sessionKey: SessionKey,
    override val source: EventSource,
    override val observedAt: Instant,
    val messageId: String
) : TranscriptEvent
```

其余事件类型建议包含：

`MessageStarted`、`ToolStarted`、`ToolUpdated`、`ToolCompleted`、`PermissionRequested`、`PermissionResolved`、`AgentStatusChanged`、`TranscriptReset`、`TranscriptGapDetected`。

需要特别保存：

- 稳定上游消息 ID。
- Provider 与 Provider 原生事件类型。
- 是否属于 Pi 的当前活动分支。
- 原始 ToolCall ID。
- 观测时间与 Provider 自身时间。
- 实际数据来源。
- 可见内容与非公开内部内容的边界。

Pi 的会话是树，不是简单线性日志。 官方 JSONL 格式使用 `id/parentId` 表示分支。这意味着手机端不能把文件中所有历史事件简单按文件顺序追加到聊天末尾；需要先确定活动分支。

## R7.8 多 Agent 适配层

### 三种方式

## R7.9 客户端模块划分

我建议拆成独立核心模块、数据层与功能层，但不要一下子制造二十多个 Gradle Module。

### 三种分层策略

| 方案                          | 优点          | 缺点                            |
| --------------------------- | ----------- | ----------------------------- |
| A. 保持现有模块，清理类职责             | 改动最少        | 大 feature 和单 ViewModel 可能继续膨胀 |
| B. 领域核心 + 数据核心 + 每屏 Feature | 边界清晰、增量迁移可行 | Gradle 与 DI 稍复杂               |
| C. 全局 Redux Store + 微模块     | 状态集中        | 单人项目容易过度工程化                   |

推荐 B。

```
:app
  ├── Navigation / AppShell
  └── DI Composition Root

:core:model
  ├── AgentState
  ├── AttentionItem
  ├── TranscriptEvent
  └── Capability / Error

:core:remote
  ├── RemoteTransport
  ├── ConnectionSupervisor
  └── SnapshotReconciler

:core:storage
  ├── Room Cache
  ├── DraftRepository
  └── WriteLedger

:core:render
  ├── Markdown IR
  ├── RichText Blocks
  └── RenderCache

:feature:inbox
:feature:agents
:feature:conversation
:feature:hosts
:feature:settings
:feature:terminal (后期)
```

这个划分允许沿用 Room、Coroutines、Flow 和已有 SSH 实现，不要求先把所有模块迁移为 KMP。

### 状态管理建议

使用：

Repository + Flow + 每屏 ViewModel + 单向事件处理。

不要在这一阶段引入全局单一 Redux Store。

- 连接状态由 Remote Repository 统一提供。
- Inbox 由 InboxViewModel 负责。
- Conversation 由 ConversationViewModel 负责。
- Host 设置由 HostViewModel 负责。
- 写操作通过独立 `CommandRepository / WriteLedger` 管理。
- 页面 ViewModel 不得持有原始 SSH Channel。

导航使用具有真正返回栈和深链能力的 AndroidX Navigation，而不是当前的 `rememberSaveable` 字符串切屏。

## R7.10 Room、缓存、持久化与错误模型

### 三种持久化策略

| 方案                       | 优点        | 缺点         |
| ------------------------ | --------- | ---------- |
| A. 只有内存缓存                | 简单        | 杀进程后失去上下文  |
| B. Room + 内存中的活动窗口       | 离线可读、性能可控 | 需要迁移与一致性管理 |
| C. 每个事件完全 Event Sourcing | 可重放       | 维护成本高      |

推荐 B，但 Companion 的事件日志可以采用轻量 Event Journal。

Room 分开存储：

- `hosts`：主机配置与身份。
- `agent_snapshots`：最近可信 Agent 状态。
- `transcript_entries`：完整消息或可分页内容。
- `attention_items`：待处理事项及生命周期。
- `drafts`：按目标保存草稿。
- `write_ledger`：远程写操作意图和回执。
- `sync_cursors`：事件序列与文件游标。

写操作账本的地位高于普通缓存：它不是可以随意清除的 UI 数据。

建议独立数据库或在当前独立草稿库中延续显式迁移，不能因重构模块而丢失以前的 Unknown 记录。

### 错误模型

至少区分：

`AuthenticationError / HostIdentityChanged / TransportDisconnected / ProtocolUnsupported / ProviderUnavailable / EventGap / StaleData / RequestRejected / DeliveryUnknown / PermissionExpired`。

不建议让 UI 直接展示未经转换的 `IOException` 字符串。

## R7.11 主线程与后台线程模型

```
Main Thread
  ├── Compose
  ├── UI state reduction
  └── user interactions

IO Dispatcher
  ├── SSH / WebSocket
  ├── File / SFTP
  ├── Room operations
  └── network requests

Default / bounded CPU pool
  ├── JSONL parse
  ├── Markdown AST
  ├── diff processing
  └── transcript normalization

Single-owner actors / serialized state
  ├── ConnectionSupervisor per host
  ├── SyncReconciler per stream
  └── WriteLedger transaction coordination
```

建议原则：

- 主线程不做网络、文件扫描或 Markdown 全文解析。
- 对同一个目标的写操作，通过独立 Actor 或队列协调，避免 ViewModel 自己并发调用。
- 各主机连接独立 Supervisor，避免一台主机断线拖垮全部首页。
- 每个流有自己的 cursor、epoch、generation。
- 解析和渲染有背压机制，不能在 UI 滚动中无限积累待处理任务。
- 分页查询尽量只把当前窗口需要的消息映射成 UI Model。

## R7.12 安全架构

### 私钥与设备密钥

有三种方案：

| 方案                                      | 安全特征        | 实现问题          |
| --------------------------------------- | ----------- | ------------- |
| A. 继续导入 OpenSSH 私钥，App 私有加密存储           | 兼容性高        | 需要保护解密密钥      |
| B. 在 Android Keystore 中生成/导入支持的不可导出密钥   | 可降低私钥提取风险   | 算法和 SSH 库必须兼容 |
| C. 使用 Companion 设备配对凭证，不要求手机保有主机 SSH 私钥 | 降低日常连接密钥复杂度 | 需要完善设备注册和撤销   |

推荐 C 作为主要用户路径，A 为传统 SSH 兼容路径。

Android Keystore 可保护密钥材料并在硬件支持时使用 TEE/StrongBox，但支持的算法、导入方式与授权参数有限制。官方 `KeyProtection` 还允许将支持的密钥对导入 Keystore。

[image](https://www.google.com/s2/favicons?domain=https://developer.android.com\&sz=32)

Android Developers+1



因此不能简单说“现有 Ed25519 OpenSSH 私钥直接放进 Keystore 就安全了”。

[待实测] 必须确认 Redmi 设备上目标算法的硬件支持情况，以及 `sshj` 是否能通过不可导出私钥句柄完成 SSH 签名。

### Companion 安全边界

建议：

- 默认只监听 Unix Domain Socket 或 `127.0.0.1`。
- 外部连接使用 SSH 隧道或经过身份验证的加密通道。
- 每台手机独立设备身份和可撤销凭证。
- 默认最低权限是只读。
- 发送指令、审批、终端接管各自独立授权。
- 所有写操作附带设备身份及审计关联 ID。
- 不允许用单个长期共享 Token 作为未来的团队权限模型。
- 远端进程不得因为收到一条 WebSocket JSON 就直接执行系统 Shell。

对于审批，再次强调：

Companion 内部的锁只能协调通过 Companion 进入的请求。它不能阻止其他人在桌面终端直接操作同一个 Agent。

如果 Provider 不支持以请求 ID 为边界的有效性检查和一次性回应，不能宣称“审批不会串题”。

| JSONL  | 半行、截断、文件轮换、UTF-8 边界               |
| Pi     | 分支切换、compaction、Tool 关联           |
| Claude | Hook 失效、权限已被其他端处理                 |
| UI     | 360/393/600/840 dp、浅深色、1.5×/2× 字体 |
| 导航     | 深链、返回栈、预测性返回、进程恢复                 |
| 安全     | 指纹变化、凭证撤销、权限不足                    |
| 性能     | 100/500/2,000 条消息、流式更新、滚动、IME     |

### R7 最终推荐

客户端

Kotlin + Compose，重新分层；按未来 KMP 共享核心的边界设计。

远程连接

主机 Companion + 持久连接，纯 SSH 兼容回退；Relay 暂不作为 V1 强制依赖。

对话

统一 `TranscriptEvent`，JSONL 兼容现有会话，ACP / SDK / app-server 作为更高能力的可选适配器。

安全

设备独立凭证、只读默认、结构化审批、Unknown 不重发、审计与撤销。

测试

JVM/截图测试覆盖绝大部分逻辑；真机专门验证操作体验与高刷新率。

R7 的关键取舍是：不牺牲已有 Herdr TUI 会话的连续性，换取更好的移动 UI。 应该通过渐进增强获得结构化能力，而不是强迫所有 Agent 迁移到新的控制协议。

# R8｜性能工程：长对话、流式渲染、网络与真机测量

## R8.1 先诊断：现有性能证据究竟说明什么？

任务书 §2.5 包含三组非常重要的数据。

| 指标                  | 当前证据                      | 可以得出的结论           | 不能得出的结论            |
| ------------------- | ------------------------- | ----------------- | ------------------ |
| 冷启动 379 ms          | `am start -W` Release 中位数 | Activity 启动链路此前较快 | 首屏业务内容 379 ms 内可见  |
| 500 条滚动 jank 30–44% | 旧版 Debug + 非严格可比滑动        | 历史版本存在严重卡顿        | 现版本 Release 仍有同样比例 |
| SFTP 353–564 ms     | 真机网络读取                    | 单次读取具有明显延迟        | 用户每次打开对话必然要等这么久    |

我认为这里最容易被忽略的不是渲染框架，而是：

UI 绘制、业务计算、数据同步和人类可感知的等待时间被混在一起了。

因此，性能工程必须首先建立四组独立指标。

Rendering

滚动是否稳定、帧是否错过截止时间、输入是否跟手。

Perceived Latency

用户点击后何时看到第一块有用内容，何时可以交互。

Network Freshness

远端变化何时到达、何时完成核验、断线后如何追赶。

Operation Correctness

操作是否送达、回执是否真实、重连是否重复执行。

这四类必须分别通过验收。不能用一次冷启动变快证明网络性能改善，也不能用流式文字看起来更快证明批准已经安全送达。

## R8.2 长对话渲染：三种方案比较

针对 500–2,000 条混合内容，我建议比较：

| 方案                              | 原理           | 预计收益     | 代价           |
| ------------------------------- | ------------ | -------- | ------------ |
| A. 继续 LazyColumn，每条消息一个 Item    | 最小改动、缓存 AST  | 可能改善部分重组 | 巨大消息本身仍昂贵    |
| B. 分页窗口 + 结构化 Block + 渲染缓存      | 将工作限制在可见内容附近 | 最值得验证    | 中等重构         |
| C. Markdown/Code 自绘 Canvas 或图片化 | 减少部分文本布局     | 特定场景可能较快 | 选择、复制、可访问性复杂 |

推荐 B。C 只作为某些超大代码输出的可选优化实验。

### 推荐渲染流水线

```
Provider raw events / JSONL
             │
             ▼
     Incremental Decoder
             │
             ▼
       TranscriptEvent
             │
             ▼
    Transcript Normalizer
             │
             ▼
     Room / Hot Window
             │
             ▼
      Render Block IR
        ├─ Paragraph
        ├─ Heading
        ├─ Code
        ├─ Table
        ├─ Tool
        ├─ Diff
        └─ Image
             │
             ▼
     Visible Lazy Window
             │
             ▼
         Compose UI
```

这一设计有三个目的：

1. 网络和文件解析不直接触发整页重建。
2. 只有可见窗口附近的内容参与排版。
3. 长工具输出、代码与表格拥有独立的降级策略。

### 我建议的六项核心优化

1\. 消息分页，而不是把 2,000 条全部作为活动 UI 状态。

Room 保存完整历史；UI 初始只展示最新约 50–100 条消息的索引和可见内容，向上滚动时按页加载旧消息。

推荐初始 `pageSize=50`，每次只追加必要页面，并利用稳定消息 ID 保持滚动锚点。

这个数字是初始测试参数，最终应由设备内存、平均消息尺寸和实际滚动时延调整。

2\. 一条大消息不能成为不可拆分的巨大 Item。

一个 ToolResult 可能包含几万到几十万个字符。

即使外层使用 LazyColumn，如果其中一项需要一次性布局 100,000 字符，LazyColumn 本身也不能解决这项布局工作。

建议将超大内容转换为分页 Block 或默认摘要，完整内容进入专门的查看器。

3\. Markdown 解析在后台完成。

解析原始文本到 AST / Block IR 由后台 CPU Dispatcher 完成。

主线程只做必要的 Compose 布局与绘制。

4\. 富文本缓存必须按内容版本失效。

现有 LRU 256 条可以继续用于验证，但应进一步考虑按字节预算而不是单纯按条数限制缓存。

例如先尝试 8–16 MiB 的 Render IR 缓存预算，再根据真实内存占用和命中率调整。

注意这不是说缓存最多只允许 16 MiB 的历史对话。完整历史仍由持久存储承担。

5\. 工具、表格和 Diff 分级渲染。

- ToolResult：默认展示摘要与少量上下文。
- Code：优先完整复制、局部可见排版，语法高亮异步。
- Table：可见部分渲染，宽表进入详情。
- Diff：文件级摘要，单文件按需展开。
- Image：异步加载、约束解码尺寸。

6\. 避免整列表高频重组。

每个可见 Item 使用稳定的 `key` 和 `contentType`，同时检查数据类的相等性开销。

Android 官方文档明确指出，现代 Compose 已启用 Strong Skipping，不应该无条件给含大型集合的模型加 `@Stable` 或 `@Immutable`。深层集合比较可能让性能反而下降。

### 文本预排版与图片化：不建议直接成为主路线

| 技术                      | 建议               | 原因                      |
| ----------------------- | ---------------- | ----------------------- |
| 后台 Markdown AST         | 采用               | 与 UI 分层清楚               |
| 按可见范围分页                 | 采用               | 控制活跃内容量                 |
| 稳定 key / contentType    | 采用               | Compose 官方建议            |
| 后台 Compose TextMeasurer | 先 Spike          | 需要验证线程安全、字体与密度一致性       |
| PrecomputedTextCompat   | 仅在 TextView 方案实验 | 不能假定直接加速 Compose Text   |

| 自绘全部 Markdown           | 暂不采用             | 维护成本和可访问性风险高            |

### 性能目标

| 指标                        | 第一阶段通过线  | 最终目标           |
| ------------------------- | -------- | -------------- |
| F500 jank                 | ≤ 10%    | ≤ 2–3%         |
| F2000 jank                | ≤ 15%    | ≤ 5%           |

## R8.4 流式输出：如何避免全表重组

现有问题的关键是：Agent 正在输出时，最后一条消息不断增长。

### 三种方案

| 方案                     | 实现   | 风险        |
| ---------------------- | ---- | --------- |
| A. 每收到 Token 就更新整个消息列表 | 最简单  | 高频重组及分配   |
| B. 将 Delta 合并后定时刷新当前消息 | 推荐   | UI 延迟几十毫秒 |
| C. 所有文字先离屏缓冲，结束时一次显示   | 性能最好 | 失去实时体验    |

推荐 B。

### 流式处理链路

```
Provider text_delta events
           │
           ▼
     DeltaAccumulator
           │
           ├─ 持续记录完整原始顺序
           │
           └─ 合并可显示文本
                    │
                    ▼
           UI Flush Scheduler
             50–100 ms
                    │
                    ▼
          ActiveMessageState
                    │
                    ▼
          更新最后一条 Item
                    │
                    ▼
           Compose Render
```

建议初始参数：

| 场景       | UI 合并间隔           |
| -------- | ----------------- |
| 用户停在对话底部 | 50–80 ms          |
| 正常阅读中    | 80–120 ms         |
| 正在快速滚动历史 | 150–250 ms，优先保证滚动 |
| App 处于后台 | 不执行 UI 刷新         |
| 消息完成     | 立即提交最终版本          |

这里的“合并间隔”只影响展示，不影响原始事件的可靠接收和存储。不能因为 UI 每 100 ms 刷新一次，就丢弃中间重要 ToolCall、审批或完成事件。

### 核心约束

- 增量写入只改变当前活动消息，历史消息 ID 与对象尽量不变。
- 语法高亮可以滞后于文本显示。
- Markdown 对未完成段落采用轻量呈现，最终段落完成后再提交完整 AST。
- 用户向上阅读时禁止自动滚动到底部。
- 只在用户原本位于底部附近时跟随新输出。
- 当页面不可见时停止高频 Compose 更新。
- 需要限制积压队列，不能无边界缓存未处理事件。

预期收益 [推断]：每秒 100 次或更高频率的 token 事件，可能只需每秒约 10–20 次 UI 刷新。理论上可显著减少 UI 更新频率，但是否降低 jank、降低多少，仍须真机测量。

## R8.5 网络往返：先算清楚现有成本

任务书中的当前设计：

- 对话 SFTP：每 1.5 秒读取一次。
- 终端预览：每 2 秒一次。
- 审批文件：每 2 秒一次。
- 单次 SFTP：5–8 个网络往返。
- 网络设计基线：RTT 50 ms。

在全部三个轮询器活跃的情况下，一分钟大约发生：

| 轮询器          | 每分钟次数         |
| ------------ | ------------- |
| Transcript   | 40            |
| Pane Preview | 30            |
| Approval     | 30            |
| 合计           | 100 次轮询/分钟/目标 |

这不是 100 个 SSH 新连接，而是 100 次相应的读取或 API 工作循环；实际 channel 数量与请求数不能直接混为一谈。

仅 Transcript 一项，理论上约产生：

`40 × 5–8 = 200–320 次 SFTP 往返等价步骤/分钟`

在 50 ms RTT 下，5–8 次串行网络往返的纯传播延迟下界为 250–400 ms，与任务书给出的 SFTP 实测 353–564 ms 属于相近量级。

[推断] 这是最值得优先消除的结构性延迟来源之一。

### 三种网络方案

| 方案                         | 对话更新       | API 调用   | 维护代价 |
| -------------------------- | ---------- | -------- | ---- |
| A. 保留 SFTP，优化 stat/read    | 仍轮询        | SSH exec | 低    |
| B. 复用 SSH channel + 主机增量推送 | 主动更新       | 复用连接     | 中    |
| C. Companion 持久 WS + 事件日志  | 主动更新 + 可恢复 | 复用连接     | 中    |

推荐 C，B 作为过渡。

### 推荐目标：首屏与会话打开

| 操作        | 原方案         | 新方案目标            |
| --------- | ----------- | ---------------- |
| 首屏展示已缓存内容 | 读取缓存        | 0 次网络往返          |
| 打开已缓存会话   | 可能等待远端文件定位  | 0 次网络往返即可显示      |
| 在线获取最新状态  | Snapshot 请求 | 订阅事件或 1 次对账请求    |
| 在线获取新文本   | SFTP 轮询     | 持久流主动增量          |
| 结构化审批     | Hook 文件轮询   | Broker 主动事件      |
| 断线恢复      | 重新各处轮询      | 事件游标回放或 Snapshot |

### 300 ms 打开会话到底意味着什么？

必须明确：

300 ms 内显示已有缓存是合理的产品目标；300 ms 内保证从任意远程主机首次读取完整新会话，则不合理。

因为你的 SSH 冷连接本身 P50 就约 500 ms。如果手机没有缓存，还要经历认证、定位 Session、获取数据、解析、落库和布局。

因此建议两个独立 SLO：

- `cachedContentVisible`：已有缓存时 P95 ≤ 300 ms。
- `freshContentVerified`：在线正常时 P95 ≤ 1 s，基于事件流或对账结果，并注明网络条件。

如果用户第一次进入从未读取过的 Agent，会话应明确显示“正在首次读取”，不能用空白屏伪装成瞬时加载。

## R8.6 Companion 端的增量读取设计

### 三种方式

| 方案                   | 延迟        | 成本 | 可靠性          |
| -------------------- | --------- | -- | ------------ |
| A. 每 1.5 秒轮询 JSONL   | 主要受轮询周期影响 | 低  | 中            |
| B. 文件系统事件通知 + 回退周期检查 | 更及时       | 中  | 推荐起步         |
| C. Provider 原生流式事件   | 最直接       | 较高 | 取决于 Provider |

推荐 B + C。

即使 Companion 读取的是 JSONL，也可以在主机本地通过文件变化通知或轻量检查获取新增内容，再主动推送给手机，避免手机每次通过 SFTP 重走文件协议。

建议记录：

`file identity + generation + byte offset + partial line buffer + active branch`

并处理：

- 文件被截断。
- 文件替换或轮换。
- 最后一行 JSON 尚未写完。
- UTF-8 多字节字符跨读取边界。
- 进程中断后恢复。
- Pi 会话切换到其他分支。
- 重复事件。
- 文件实际已不存在或权限改变。

### 文件与事件去重

不要只用时间戳去重。

建议优先采用 Provider 自带的稳定消息 ID。没有稳定 ID 时，可以定义带源文件身份、Generation、Offset 的内部标识，但必须允许文件重建时重新对账。

JSONL 原始字节位置、Provider 消息 ID 与 UI Message ID 不应该被混成同一个概念。

## R8.8 MIUI 真机测量：不依赖 Macrobenchmark 的方案

这是本轮最关键的工程落地点。

### 现状

按照任务书，你的 MIUI 真机阻止 instrumentation 启动 Activity，但 `adb` 手动启动应用正常。

因此我建议建立一条不依赖 AndroidTest Instrumentation 启动 Activity的基准测量链路。

### 三种测量方案

| 方案                                         | 依赖                             | 能测什么                    | 推荐         |
| ------------------------------------------ | ------------------------------ | ----------------------- | ---------- |
| A. `dumpsys gfxinfo` + `input swipe`       | 最少                             | 粗略图形数据                  | 辅助，不作为正式回归 |
| B. App 内 JankStats + Perfetto + 测试 Fixture | 无需 instrumentation 启动 Activity | 帧、线程、布局与滚动              | MIUI 主方案   |
| C. 第二台兼容设备的 Macrobenchmark                 | 需要另一台设备                        | 自动化 Startup/FrameTiming | CI/回归辅助    |

推荐 B + C。

[事实] JankStats 可以报告逐帧 jank 和耗时，Perfetto FrameTimeline 可分析实际与预期帧；Android System Tracing 支持在真机上直接采集 Perfetto 格式追踪，不必一定先通过 instrumentation 启动 App。

- `debuggable=false`
- `profileable by shell=true`
- R8 配置与实际 Release 一致
- 可读取内置 Fixture
- 可由 `adb shell am start` 打开指定测试页
- 不连接真实 SSH 主机，不暴露私钥
- 只记录时间与计数，不记录用户对话内容

这个构建应当有独立包名或明确的测试标识，并且不能把任何测试入口意外打包到生产 Release。

### 一个可行的 ADB 测试入口

以下是拟议中的命令接口，须由本地 Agent 实现对应 Deep Link 才能运行：

```
adb shell am start \
  -a android.intent.action.VIEW \
  -d 'herdr-bench://conversation?fixture=2000&scenario=scroll' \
  com.example.herdr.benchmark
```

App 启动后直接进入指定 Fixture 的对话页面，无需手动添加主机、登录或者等待网络。

页面提供明确的“开始测试”操作，或通过只在 benchmark variant 启用的测试控制器自动执行固定滚动路径。

### 采集三种证据

第一种：JankStats 事件

记录每帧：

`scenario_id、frameStart、frameDurationUi、frameOverrun、isJank、displayRefreshRate`

官方文档指出 `FrameData` 可能被复用，回调应快速返回；不能把该对象引用直接塞进异步队列后继续使用。

[image](https://www.google.com/s2/favicons?domain=https://developer.android.com\&sz=32)

Android Developers



建议在回调中复制必要数值到轻量环形缓冲区，测试结束再统一汇总。

第二种：Perfetto 系统追踪

可在设备的开发者选项中启用 System Tracing，手动执行固定滚动场景并导出 Trace。

分析时查看：

- Main Thread
- RenderThread
- FrameTimeline Expected / Actual
- CPU 调度与线程抢占
- GC
- 布局 / 文本相关 Trace Section
- Compose 运行区间

Perfetto FrameTimeline 是 Android 12 及以后用于分析实际显示帧 jank 的官方工具链之一。

[image](https://www.google.com/s2/favicons?domain=https://perfetto.dev\&sz=32)

Perfetto Tracing Docs



第三种：应用内部业务耗时

使用单调时钟记录：

- `navigationRequested`
- `cachedDataLoaded`
- `firstUsefulContentRendered`
- `firstInputReady`
- `remoteSnapshotReceived`
- `transcriptIncrementApplied`
- `writeCommandSubmitted`
- `writeAcknowledged`

同设备内用单调时间计算耗时，不要把不同设备的 wall-clock 时间戳直接相减。

### 启动测量特别处理

`am start -W` 可以继续保留，作为辅助的 Activity 启动指标。

但要新增：

- 第一帧出现时间。
- 首屏有用缓存内容出现时间。
- 首屏能够处理点击时间。
- 在线最新数据核验完成时间。

这些不同事件不能混成一个“冷启动耗时”。

## R8.9 测试场景与重复次数

建议针对同一台 Redmi 建立如下实验矩阵。

| 场景                 | 测试内容                        | 推荐重复   |
| ------------------ | --------------------------- | ------ |
| Cold Start         | Force-stop 后启动              | 20 次   |
| Warm Start         | 后台切回前台                      | 20 次   |
| Inbox              | 5、20、100 Agent              | 各 10 次 |
| Conversation F100  | 连续滚动                        | 10 次   |
| Conversation F500  | 连续滚动                        | 10 次   |
| Conversation F2000 | 连续滚动                        | 10 次   |
| Stream             | 模拟 20、50、100 delta/s        | 各 10 次 |
| IME                | 键盘开合与发送                     | 20 次   |
| Navigation         | Inbox ↔ Conversation ↔ Diff | 20 次   |
| Reconnect          | 断线 5/30 秒后恢复                | 各 10 次 |

每次记录环境：

- 实际显示刷新率（不是只看设置里选择了 120 Hz）。
- 电池电量与省电模式。
- 设备温度或至少热状态。
- 构建版本和 R8 状态。
- Fixture ID 与固定随机种子。
- 是否启用 Baseline Profile。
- 是否网络在线。
- 当前是否有后台重型任务。

推荐采用连续对照，而不是“今天测旧版、下周测新版”。

旧版和新版交替测量更有助于减少设备温度、系统缓存等因素造成的偏差。

### 最终性能报告必须分开记录

| 指标                        | 含义                      |
| ------------------------- | ----------------------- |
| `jankRate`                | JankStats 判定的 janky 帧比例 |
| `frameUiP50/P95/P99`      | UI 侧帧耗时分位数              |
| `frameOverrunP50/P95/P99` | 截止时间超出情况                |
| `presentedFrameRate`      | 实际显示帧率                  |
| `cachedFirstContentP95`   | 本地缓存首显                  |
| `remoteFreshnessP95`      | 在线数据核验                  |
| `streamDisplayLagP95`     | 事件抵达手机到 UI 显示           |
| `writeAckP95`             | 发送到明确回执                 |
| `memoryPeak`              | 场景峰值内存                  |
| `gcPause`                 | GC 暂停                   |
| `cpuTime`                 | 主要线程 CPU 消耗             |

对于 jank 率，分母只统计场景中的有效帧，排除开始、结束和非测试阶段；每轮必须记录有效帧数量，避免用 20 帧就宣称达到 1% jank。

## R8.10 网络弱网实验

在专用测试环境中模拟：

| 网络场景 | RTT       | 丢包 | 目标         |
| ---- | --------- | -- | ---------- |
| N1   | 20 ms     | 0% | 良好网络       |
| N2   | 50 ms     | 0% | 当前设计基线     |
| N3   | 150 ms    | 1% | 普通较差移动网络   |
| N4   | 300 ms    | 3% | 严重弱网       |
| N5   | 中断 5–30 秒 | —  | 重连与恢复      |
| N6   | 进程被杀后重新启动 | —  | 游标恢复与写操作核对 |

建议使用独立测试主机上的网络模拟或专用代理，不直接在生产开发机网络接口上修改 `tc` 队列规则。

### 重点验收

- 断线后首页保留缓存。
- 数据 Freshness 正确降级。
- 事件恢复不丢、不重、不乱。
- 同一 ToolCall 不出现重复卡片。
- 未完成 JSONL 行不会被当作解析失败。
- 未确认写操作不自动重发。
- 旧的审批请求不会因恢复连接突然重新变成可操作。
- 网络恢复后能通过日志游标或快照对账恢复可信状态。

## R8.11 哪些优化值得最先尝试？

我的优先级判断如下：

| 优先级 | 优化                        | 为什么                  |
| --- | ------------------------- | -------------------- |
| P0  | 建立 Release + R8 的可靠性能基线   | 现有 jank 数据不可直接用于架构决策 |
| P0  | JankStats + Perfetto 真机测量 | 否则不知道是否真的改善          |
| P0  | Room 缓存优先显示               | 立刻改善感知延迟             |
| P0  | 避免整表重组                    | 流式场景最大潜在收益之一         |
| P1  | 分页与 Block 级渲染             | 解决超长历史和巨型消息          |
| P1  | Markdown 后台解析             | 缩短主线程工作              |
| P1  | Companion 增量推送            | 降低对 SFTP 轮询的依赖       |
| P2  | Baseline Profiles         | 提高启动与常用路径稳定性         |
| P2  | 高亮延迟 / diff 虚拟化           | 优化重型内容               |
| P3  | 自绘、图片化、替换 UI 引擎           | 只有测量支持时才做            |

特别反对一开始就做三个事情：

一是全面使用 `@Stable`、`@Immutable`，二是给所有消息做预测量，三是把 Markdown 全部改为图片或 WebView。

它们听起来像“高性能架构”，但在现有证据不足时，都可能引入额外计算与长期维护成本。

## R8.12 给本地 Agent 的性能诊断优先任务

在正式实施 R7 的 Companion 之前，我建议先完成一个非常具体的 Performance Baseline Spike。

Spike：验证 Compose 是否需要更换

优先级 P0

目标是建立可信性能证据，不改交互、不换框架、不动远程写操作。

实施范围

1. 新增独立 benchmark 构建变体。
2. 使用固定 F100/F500/F2000 Fixture。
3. 增加 JankStats 指标收集。
4. 真机采集 Perfetto，确认实际刷新率。
5. 对比现有 Markdown 渲染和纯文本渲染。
6. 比较 R8 开/关，并回归 SSH 密钥与序列化功能。
7. 输出原始数据、P50/P95/P99、Trace 文件和截图。

   验收结果

   能够明确指出 jank 的主要时间消耗来自 Composition、Layout/Text、Draw、GC、调度还是其他任务；如无法定位，必须记录为未核实。

不能再用“看起来更流畅”或单次 `dumpsys gfxinfo` 数值作为最终证明。

### 对性能根因的三个假设

| 假设                 | 当前依据               | 验证                         |
| ------------------ | ------------------ | -------------------------- |
| H1：Debug/JIT 影响很大  | 旧滚动结果主要来自 Debug    | Release + R8 对照            |
| H2：长文本测量/布局是瓶颈     | 早期去阴影、去卡片仍卡顿       | Perfetto Layout/Text Trace |
| H3：状态观察与整表更新造成额外开销 | 当前 UI、数据和多个同步循环较复杂 | 本地 Fixture 隔离网络 + 重组分析     |

这些只是待实测假设，不能当作已发现的 bug。

# R6–R8 综合决策

| 领域     | 建议冻结的方向                       | 不应提前冻结的内容                |
| ------ | ----------------------------- | ------------------------ |
| 动效     | 克制、局部、可降级                     | 各设备最终时长                  |
| UI 技术栈 | 暂保留 Kotlin/Compose            | 永久放弃跨平台                  |
| 连接     | Companion 为目标架构               | Rust/其他语言的最终实现           |
| 网络协议   | 持久双向连接、可恢复事件                  | Envelope 具体字段与编码         |
| 对话源    | 多 Provider Adapter + 统一事件 IR  | 某个 Provider 统一取代所有 JSONL |
| 审批     | 请求绑定、过期校验、真实回执                | 未验证 Hook 的快捷批准能力         |
| 本地数据   | Room 缓存 + 独立 WriteLedger      | 当前所有表结构原样保留              |
| 渲染     | 分页、Block 化、后台解析               | 图片化代码和全文预排版              |
| 性能测量   | JankStats + Perfetto + 第二设备回归 | 未经测试的具体加速倍数              |

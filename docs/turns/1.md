# R3｜7 个关键屏幕线框

## R3.1 首先定义全局布局约束

你的目标使用环境是 6.7 英寸手机、单手操作、网络不稳定、经常需要快速回答 Agent 的问题。

我建议先按 360 dp 宽的紧凑窗口设计，再验证 393、412、600、840 dp 等尺寸。360 dp 只是原型测试基准，不能直接从 1080×2400 的像素分辨率推断设备 dp。

[事实] Android 官方以窗口宽度而非物理设备尺寸定义自适应布局：紧凑宽度小于 600 dp，中等宽度为 600–839 dp，扩展宽度从 840 dp 起。官方 Compose 无障碍指南推荐可交互区域至少 48×48 dp。

### 三种错误呈现方式

| 方案              | 优点   | 缺点      | 推荐场景       |

# R4｜视觉语言与品牌设计

## R4.1 首先明确：为什么上一版 Graphite × Editorial 不够好？

[事实：来自任务书] 现有界面使用浅灰背景、蓝色强调色、分组看板、16 dp 圆角、系统字体以及较少的自定义动画。

但“目前不够精致”是你的使用反馈，不能仅通过这些 token 推导出唯一原因。

我认为需要区分三个可能的问题：

| 假设           | 可能表现            | 验证方法               |
| ------------ | --------------- | ------------------ |
| H1：视觉语言缺乏独特性 | 像通用 Material 模板 | 同内容、不同视觉方案盲评       |
| H2：层级和布局不合理  | 看上去拥挤、重点不明显     | 灰度截图与 3 秒识别测试      |
| H3：交互反馈不足    | 觉得页面很“硬”“粗糙”    | 同一 UI 对比有/无动效与交互反馈 |

[推断] 我倾向认为 H2 和 H3 比具体颜色更重要。

即使换一套漂亮配色，只要首页仍然塞满状态、卡片、标签、技术字段，用户看到的仍会是一个工程控制台。

因此，本轮设计要求是：少用视觉元素，但让每个元素有明确作用。

## R4.2 三套完整方向

Attention

## A. Quiet Signal

安静、精确、可靠

冷中性背景、靛蓝强调、严格信息栅格。接近专业效率工具的清晰感，但刻意减少装饰。

适合：希望保留当前品牌的专业感，降低迁移风险。

Attention

## B. Warm Ledger

温润、克制、有秩序

暖纸白、深墨色、低饱和紫色强调，利用文字和留白建立层级，让移动端开发工具更像精心设计的个人工作空间。

适合：希望与现有蓝灰色开发工具拉开差异，形成长期品牌。

Attention

## C. Signal Lab

现代、清透、轻快

深青色主色、清亮表面、简洁几何。整体更年轻，适合强调实时反馈、多个 Agent 并行工作的产品个性。

适合：更看重现代科技气质和轻快的互动感。

以上均为我提出的原创设计方向，不是竞品的官方设计系统。具体视觉偏好仍需原型比较。

## R4.4 WCAG AA 对比度验证

[事实] WCAG 2.2 AA 规定，普通文字和背景至少 4.5:1，大号文字至少 3:1；用于识别交互控件或承载必要信息的非文字视觉元素通常需要至少 3:1。颜色也不能是表达状态的唯一手段。

我使用 WCAG 相对亮度公式对上述色值进行了计算，结果如下。

显示值四舍五入至两位小数；同色板中的角色必须按指定背景组合使用。

| 对比项                         | A     | B     | C     | AA 门槛 |
| --------------------------- | ----- | ----- | ----- | ----- |
| 浅色主文字 / Background          | 14.91 | 14.00 | 13.66 | 4.5   |
| 浅色次文字 / Surface             | 7.58  | 7.27  | 7.97  | 4.5   |
| 浅色 On Accent / Accent       | 7.94  | 7.98  | 6.09  | 4.5   |
| 浅色 Strong Outline / Surface | 3.59  | 3.47  | 3.24  | 3.0   |
| 深色主文字 / Background          | 17.00 | 15.93 | 17.02 | 4.5   |

这些组合满足相应数值门槛，但不代表整个 App 已满足 WCAG AA。还要验收全部状态色、透明叠层、禁用态、代码高亮、图片叠字、焦点边框、图标、文字缩放和 TalkBack。

另外，表中的 `Strong Outline` 专门用于需要对比度的控件边界和焦点，装饰性浅分隔线可以更柔和，但不得承担唯一的控件识别职责。

## R4.5 字体与字阶

不建议第一阶段引入需要单独维护的商业字体，优先使用 Android 系统无衬线字体及系统等宽字体，保留自动回退和大字体支持。

# R5｜组件规范（Design System v0.1）

这一节比配色更重要。

我建议 Herdr 的 Design System 不是简单的颜色、按钮、卡片集合，而是一套能正确表达 Agent 运行状态、远程连接与操作结果的语义组件系统。

否则很容易出现一种危险情况：界面做得越来越精致，但状态表达实际上比原先更不准确。

## R5.1 先定义五个独立状态维度

必须把下面五个维度从数据模型上分开。

| 维度             | 回答的问题        | 示例                                               |
| -------------- | ------------ | ------------------------------------------------ |
| Agent Runtime  | Agent 正在做什么？ | blocked / working / done / idle / unknown        |
| Connection     | 手机与主机能否通信？   | online / reconnecting / offline                  |
| Freshness      | 当前显示的信息有多可靠？ | verified / cached / unknown                      |
| Attention      | 哪件事需要人处理？    | question / permission / review / uncertain_write |
| Write Delivery | 用户的操作是否送达？   | sending / accepted / rejected / unknown          |

[事实] Herdr 自身的 Agent 状态只有任务书 §3.1 中的五种。

[推断] 其余四个维度应由客户端与未来的 Companion 显式维护，不能从 Agent 状态直接推导。

例如：

Claude · ParseDock

等待用户

连接已恢复

缓存状态

上次确认等待中 · 8 秒前

尚未核对请求是否仍有效，暂不能批准。

这个例子表达了三个同时成立的事实：Agent 上次处于等待状态、通信已经恢复、但等待请求尚未重新确认。

不能将整个组件简化成一个绿色的“已连接”状态。

### AgentRow 的数据契约

```
data class AgentRowUiState(
    val agentKey: String,
    val displayName: String,
    val projectName: String?,
    val runtimeState: AgentRuntimeState,
    val summary: String?,
    val attentionCount: Int,
    val waitingSince: Instant?,
    val waitingSinceVerified: Boolean,
    val lastVerifiedAt: Instant?,
    val freshness: Freshness,
    val canOpen: Boolean
)
```

这是 UI 侧建议接口，不是已经存在于 Herdr 协议中的结构。

关键约束：

- `waitingSince == null` 时，禁止生成虚假等待时长。
- `runtimeState == blocked` 不代表 `attentionCount > 0`。
- `freshness != verified` 时，不显示“实时”。
- `canOpen` 仅控制导航，不代表可以执行远程操作。

## R5.4 AttentionCard：需要人处理的事项

建议显式区分四种事项。

| Kind                 | 说明           | 默认行为        |
| -------------------- | ------------ | ----------- |
| `permission_request` | 有结构化权限请求     | 查看/批准/拒绝    |
| `question`           | Agent 提出明确问题 | 查看/回答       |
| `review_required`    | 需要检查成果       | 查看 diff 或结果 |
| `uncertain_write`    | 用户操作结果未知     | 核对，禁止自动重发   |

再单独处理 `blocked_unresolved`：Herdr 判断 Agent 阻塞，但尚无可靠结构化请求。它可以出现在 Inbox，但不能伪装成可点击的审批卡。

### 操作取舍

| 方案                  | 用户效率 | 安全性      | 推荐   |
| ------------------- | ---- | -------- | ---- |
| A. 所有卡片都直接放批准按钮     | 高    | 风险大      | 不采用  |
| B. 仅满足原子请求绑定条件时快捷操作 | 高    | 可控       | 推荐   |
| C. 所有操作都进入会话        | 较低   | 可获得更多上下文 | 作为回退 |

AttentionCard 的最低信息集：

请求类型、所属 Agent、项目名称、完整或可展开的请求摘要、请求有效性、数据新鲜度、可执行动作。

如果是执行命令，还需要准确展示命令本身、工作目录、目标环境及请求的授权范围。无法核实的字段必须标注“未提供”，不能由模型猜测。

### 生命周期

```
Observed（观察到）
      │
      ▼
AwaitingValidation（待验证）
      │
      ├── 验证成功 ──▶ Actionable（可操作）
      │                    │
      │                    ├── 提交回应
      │                    │      ├── Resolved
      │                    │      ├── Rejected
      │                    │      └── OutcomeUnknown
      │                    │
      │                    └── 远端先行处理 ──▶ Resolved
      │
      ├── 已失效 ──▶ Expired / Resolved
      └── 无法验证 ──▶ ReadOnlyUnknown
```

`Actionable` 必须依据实际 provider 的协议能力得出，而不是由读屏结果触发。

对于没有原子回应语义的 provider，即使拥有 request ID，也只能被判定为较弱的可操作能力，不能直接套用强安全保证。

## R5.5 对话消息组件系统

这是整个 UI 工程中最复杂、最容易导致滚动性能恶化的部分。

建议定义统一的 `MessageBlock`，再根据类型渲染，而不是直接把所有 JSONL 转成一个巨大的 Markdown 字符串。

### 消息类型规范

| 类型          | 默认呈现        | 操作         | 性能约束        |
| ----------- | ----------- | ---------- | ----------- |
| User        | 右侧气泡        | 复制、引用      | 只布局自身       |
| Agent       | 全宽文档式       | 复制、引用、更多   | 分块解析        |
| Thinking    | 一行折叠入口      | 展开（若数据允许）  | 默认不组成内部文本   |
| Tool Call   | 工具标题 + 参数摘要 | 展开参数       | 参数按需布局      |
| Tool Result | 状态 + 输出摘要   | 查看全文、复制    | 长输出虚拟化或独立详情 |
| Code        | 等宽块         | 复制、横向滚动    | 延迟高亮        |
| Diff        | 文件摘要与增删行数   | 查看逐文件 Diff | 文件级展开       |
| Table       | 可滚动表格       | 复制、全屏查看    | 避免一次测量巨大表格  |
| Image       | 缩略图与尺寸      | 查看原图       | 异步解码        |
| Error       | 错误类型、上下文    | 查看详情、复制诊断  | 不渲染无边界长堆栈   |

### 5.5.1 用户消息与 Agent 消息

方案比较：

| 方案      | 优点      | 缺点             |
| ------- | ------- | -------------- |
| A. 全气泡  | 统一、容易实现 | 工具输出和 diff 很别扭 |
| B. 全文档流 | 技术内容友好  | 难以区别人的输入       |
| C. 混合结构 | 最适合编程对话 | 需要维护多种组件       |

推荐 C。

具体规格：

- 用户气泡宽度不超过内容区 84%，内边距 12–14 dp，圆角 14 dp。
- Agent 回复使用内容区全宽，段落间距 8–12 dp。
- Agent 正文 16 sp / 26 sp，代码使用 14 sp / 22 sp（Warm Ledger）。
- 消息之间的主间距 20–24 dp。
- Agent 消息尾部“复制 + 更多”保持低视觉权重，但每个操作触控区仍不小于 48×48 dp。
- 长按正文进入系统文本选择，不能被整条消息的自定义长按菜单截获。

### 5.5.2 ToolCall 与 ToolResult

建议不要将工具调用拆成两个完全独立的大卡片。

&#x20;执行测试

&#x20;已完成

pytest tests/ -q

Exit 1

128 passed

1 failed

查看完整输出

调用和结果只有在拥有可靠 `toolCallId`（或经过验证的 provider 等价关联标识）时才配对。否则分别展示，不能凭时间顺序猜测。

工具状态建议至少有：

`queued / running / succeeded / failed / cancelled / outcome_unknown`

这些是客户端规范化状态，不等于每个 Agent 原生协议都支持全部六种。无证据时只能映射为 unknown。

### 5.5.3 Thinking

推荐默认折叠：

- 标题：“思考过程”或“内部推理信息”
- 仅在 provider 合法提供可展示内容时才可展开。
- 不将不可获取的内部推理伪造为摘要。
- 不提供无限闪烁的“正在思考”动画。
- 正在处理时可以展示静态文案及短时状态变化。

### 5.5.4 Diff

建议三个层次：

文件改动

2 个文件

+38

−12

src/parser/worker.py

+31 −8

tests/test_worker.py

+7 −4

推荐：摘要 → 文件列表 → 单文件 Diff。

### 5.5.5 Code、Table、Image

建议参数：

| 组件       | 推荐限制                |
| -------- | ------------------- |
| Code 预览  | 默认展示前 12–16 行，可展开   |
| 代码字号     | 14 sp / 22 sp       |
| 代码区域     | 独立横向滚动，避免强制软换行改变语义  |
| Table 预览 | 首屏最多展示 5–8 行，更多进入详情 |
| 宽表格      | 横向滚动，首列可选固定         |
| Image 预览 | 宽度占内容区，按比例约束最大高度    |
| 长输出      | 独立详情 + 搜索，不一次加载全部   |
| 图片加载     | 有占位、加载失败和重试状态       |

这些是 UI 预算，不是数据截断限制。必须能够访问完整原始信息。

[事实] Compose 官方性能指南建议在异构 Lazy 列表中使用稳定 `key`、`contentType`，以减少无效重组和帮助复用；官方也强调 debug 构建不足以评估最终滚动性能。

## R5.6 Composer：输入栏

### 三种方案

| 方案                | 复杂度 | 长期扩展 | 推荐    |
| ----------------- | --- | ---- | ----- |
| A. 极简单行输入         | 最低  | 有限   | 不足    |
| B. 自适应多行 + 可用能力入口 | 中   | 高    | 推荐    |

## R5.10 加载、空态与反馈组件

### 加载方式的取舍

| 方案                 | 优势   | 缺点          |
| ------------------ | ---- | ----------- |
| A. 每次打开显示 Skeleton | 易于统一 | 缓存明明存在却造成闪烁 |
| B. 缓存先展示，后台同步      | 操作连续 | 需要管理数据新鲜度   |
| C. 一直等待远端成功        | 数据更新 | 弱网很差        |

推荐 B。

建议组件行为：

| 情况          | 表现                  |
| ----------- | ------------------- |
| 有缓存         | 立即显示内容，并标记缓存/核验状态   |
| 无缓存，短暂加载    | 保留页面结构，避免空白闪烁       |
| 无缓存，持续加载    | Skeleton + 明确“正在读取” |
| 网络失败        | 可用缓存 + 重连入口         |
| 无任何 Agent   | 引导连接主机或检查 Session   |
| 无待办但有 Agent | 正向空态 + 查看运行中        |
| 无待办且全主机离线   | 不显示“全部处理完毕”，显示无法确认  |

最后一项非常重要。

“没有待办数据”不等于“没有等待中的 Agent”。 如果所有主机都离线，页面必须明确说“当前无法确认是否存在新的待处理事项”。

## 对 A1–A10 旧决策的阶段性影响

本轮研究最明确地支持推翻 A6：状态看板作为默认首页，以及重新设计 A5：审批文件轮询在客户端的呈现和可用性边界。

对于 A7（自研 Markdown）和 A8（客户端分层），R5 已经提出新的组件契约，但还不能在没有性能数据和代码检查的情况下判定应选择哪个具体 Markdown 库，也不能直接确定所有模块边界。这些应在 R7–R8 评估。

对于 A1（Kotlin 原生）和 A2（无主机组件），仍维持 R0 的暂定推荐：保留 Kotlin/Compose，优先研究引入轻量 Companion。
